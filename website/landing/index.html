Health-data infrastructure in Rust, built on open standards.

FerroHEALTH is the family behind three servers that do one job each and run beside each other: a record server that speaks openEHR, a terminology server that speaks HL7 FHIR, and a bridge that carries a record out to FHIR and to the OMOP Common Data Model. No JVM, no language runtime, no search cluster.

See the three products Try the live sandbox

Ferro is ferrum, iron. Rust is an oxide of it, which is the language all three are written in.

The products

Three servers, one at a time

Each one is its own repository, its own release train, and its own site. Run the one you need; nothing here requires the other two.

FerroEHR

The record
Released

An openEHR Clinical Data Repository. Applications store and query structured health records through a vendor-neutral REST API and the Archetype Query Language, so the record outlives the application that wrote it.

  • ITS-REST 1.1.0 and AQL 1.1, generated from the official machine-readable models
  • Contribution-atomic versioning, attestations and per-version signatures
  • One self-contained binary on PostgreSQL 18, no JVM in the write path
  • Every conformance claim run against the live server each release
ferroehr.eu GitHub

FerroTERM

The meaning
Released

An HL7 FHIR terminology server. It answers the FHIR terminology API from one static binary over a memory-mapped index built once per release, which is what lets a full SNOMED CT edition run on ordinary hardware.

  • SNOMED CT, LOINC, ICD-10, ICD-11, RxNorm, UCUM and any FHIR CodeSystem
  • FHIR R4, R4B, R5 and the R6 ballot through one provider seam
  • No JVM, no Elasticsearch, no database to run
  • Every published figure rendered from a committed benchmark record
ferroterm.eu GitHub

FerroBRIDGE

The way out
Design phase

A bridge from openEHR to two targets: HL7 FHIR, and the OMOP Common Data Model for research. Mappings are specification-conformant YAML validated against published schemas, never hand-coded per resource or per table.

  • FHIRconnect for the FHIR side, OMOCL for the OMOP side
  • Its own process beside any CDR it reaches over ITS-REST, never a plugin
  • A FHIR facade that stores nothing, and a batch ETL that writes typed rows
  • Designed and written down; no binary yet, and the site says so
ferrobridge.eu GitHub
How they fit

What calls what

Every arrow is a published specification, so any one of the three can be swapped for another implementation of the same standard.

An arrowhead points at what is called or written to, and the FHIR side carries one at both ends because the bridge reads openEHR out to FHIR and writes FHIR back in. FerroEHR and FerroBRIDGE both call a FHIR terminology server: FerroEHR to validate a coded value at commit time, FerroBRIDGE to resolve a display, translate a code and validate one. That seam is the FHIR terminology API, so FerroTERM fills it and so does any other implementation. The facade is R4 because FHIRconnect's schemas admit no other version for a mapping. OMOP is a database schema, so its edge names no protocol: the OMOCL mappings compile to SQL that writes typed rows into the CDM v5.4 tables.

What the family holds in common

The same four commitments in all three repositories

The three differ in what they do. They are built, licensed and evidenced the same way.

The standard is the interface

openEHR for the record, HL7 FHIR for exchange and terminology, OMOP for research. Where a specification publishes a machine-readable model, the code is generated from it, so a specification update is a regeneration.

One licence, no open-core tier

Every product is source-available under the Business Source License 1.1, with each capability in one repository and nothing held back for a paid edition. Free for non-commercial production; other production use needs a commercial licence, and each version becomes Apache 2.0 four years after it is published.

Measured, never typed

Conformance verdicts and performance figures are rendered into these sites from records committed to the repository, and a check fails the build when a page and its records disagree. Every number on these sites comes from a run.

One binary to operate

Each server is a single self-contained Rust binary in a minimal distroless image: no application server, no language runtime to patch, and no garbage-collection pause in the request path. What you deploy is what you read.

Quick start

Both released servers, from a container

Nothing to check out and nothing to configure. Each product's site carries the full installation, the configuration, and the licensing each code system needs.

shell 
# FerroTERM. The image serves UCUM, BCP 47, BCP 13 and ISO 3166-1
# with no configuration, so the first call needs nothing else.
$ docker run --rm -p 8080:8080 ghcr.io/rubentalstra/ferroterm:0.0.11
$ curl 'http://localhost:8080/r4b/CodeSystem/$lookup?system=http://unitsofmeasure.org&code=mg/dL'

# FerroEHR. The server and PostgreSQL 18 from the compose file
# shipped with the latest release, in the current directory.
$ docker compose up
$ curl http://localhost:8080/ferroehr/rest/status
