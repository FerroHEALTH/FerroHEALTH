Health-data infrastructure in Rust, built on open standards.

FerroHEALTH is the family behind four servers that do one job each and run beside each other: a form builder that a clinician types into, a record server that speaks openEHR, a terminology server that speaks HL7 FHIR, and a bridge that carries a record out to FHIR and to the OMOP Common Data Model. No JVM, no language runtime, no search cluster. Four more are planned around them: who the patient is, who may act, where else the record is, and how it all runs.

See the four products Try the live sandbox

Ferro is ferrum, iron. Rust is an oxide of it, which is the language all four are written in.

The products

Four servers, one at a time

Each one is its own repository, its own release train, and its own site. Run the one you need; nothing here requires the other three.

FerroCHART

The way in
v0.1.0

An openEHR form builder and renderer. It compiles an operational template into a form, renders it for a clinician, and turns what they type back into a COMPOSITION, so the last mile between a clinical model and a person is not hand-built per form.

  • Fields derived from the Reference Model type at each template node
  • Hand-authored layout in a separate overlay, so a template revision does not destroy it
  • Any openEHR CDR over ITS-REST, never a plugin inside one
  • The round trip to a real CDR runs in CI on every pull request
ferrochart.eu GitHub

FerroEHR

The record
v4.3.0

An openEHR Clinical Data Repository. Applications store and query structured health records through a vendor-neutral REST API and the Archetype Query Language, so the record outlives the application that wrote it.

  • The openEHR REST API and AQL, generated from the official machine-readable models
  • Contribution-atomic versioning, attestations and per-version signatures
  • One self-contained binary on PostgreSQL, no JVM in the write path
  • Every conformance claim run against the live server each release
ferroehr.eu GitHub

FerroTERM

The meaning
v0.1.3

An HL7 FHIR terminology server. It answers the FHIR terminology API from one static binary over a memory-mapped index built once per release, which is what lets a full SNOMED CT edition run on ordinary hardware.

  • SNOMED CT, LOINC, ICD-10, ICD-11, RxNorm, UCUM and any FHIR CodeSystem; its site carries the full list
  • Several FHIR releases from one binary, each under its own path, and a web viewer in the same binary
  • No JVM, no Elasticsearch, no database to run
  • Every published figure rendered from a committed benchmark record
ferroterm.eu GitHub

FerroBRIDGE

The way out
v0.0.2

A bridge from openEHR to two targets: HL7 FHIR, and the OMOP Common Data Model for research. Mappings are specification-conformant YAML validated against published schemas, never hand-coded per resource or per table. The design is written down and the tracker on GitHub is the live record of the build.

  • FHIRconnect for the FHIR side, OMOCL for the OMOP side
  • Its own process beside any CDR it reaches over ITS-REST, never a plugin
  • A FHIR facade that stores nothing, and a batch load that writes typed rows
  • Every decision carries its citation, in the architecture document and on the tracker
ferrobridge.eu GitHub

FerroPIX

Who the patient is

A Master Patient Index. Every organisation issues its own identifiers for the same person, and records move, so one service holds the cross-reference and the record's location and answers the question every other component starts with.

  • IHE PIX and PDQ, and their FHIR forms PIXm and PDQm, so an integrator finds the surface they expect
  • Its own store, outside the CDR, so the clinical record carries little that identifies a person directly
  • The EHR Index of the openEHR Platform Service Model, as a separate server
  • Fed by FerroEHR when an EHR is created or its subject changes, and asked by FerroFED and by the application that opens a record; FerroCHART receives the EHR it is launched with and asks nobody

FerroSMART

Who may act

The SMART on openEHR server. FerroEHR carries that layer today: the discovery document, the launch context, the scope grammar and the gate that enforces it on every request. FerroSMART pulls it out into a server of its own, so one place owns authorisation for the whole family and each server asks it about the token it is handed.

  • OAuth 2.0 and OpenID Connect for every client, human or machine
  • SMART on openEHR and SMART App Launch: the discovery document, the launch context and the scopes, served once for every server
  • An app registry: which clients exist, and what each may ask for
  • Token introspection for FerroEHR, FerroTERM and FerroBRIDGE, so a scope is enforced the same way at every door
GitHub ferrosmart.eu code moved 2026-09-14

FerroFED

Where else the record is

A federation gateway. A record held by another organisation is out of reach today. This service discovers the patient across sites and queries the record where it lives, and it keeps no second copy that could compete with the source.

  • A transparent ITS-REST intermediary: a client sends an ordinary AQL query and never learns it was federated
  • The patient is resolved first, through FerroPIX, so no directly identifying identifier travels in a query
  • Standard AQL to each node, the local FerroEHR or a remote CDR, scoped to that node's own EHR id and merged with its provenance
  • Its own process beside the CDR, over the published API and never a plugin
GitHub ferrofed.eu code moved 2026-09-14

FerroSYS

How it all runs

The control plane. It touches no clinical content and carries what every server would otherwise invent for itself: health and readiness across the deployment, telemetry, the event log, notification subscriptions, and how the whole is installed, configured and deployed.

  • Liveness and readiness for every server, in one place
  • One event log and one subscription service, so no component invents its own delivery
  • Telemetry and dashboards for the deployment as a whole
  • Installation, configuration and deployment of the family as one unit

How they fit

What calls what

Every arrow is a published specification, so any one of them can be swapped for another implementation of the same standard. Solid is a server you can run today; dashed is planned.

The frame is one FerroHEALTH instance serving one tenant: the eight inside are the family, and everything outside is a caller, a target or another organisation. FerroEHR can host several isolated tenants in one deployment as its own setting; the family shows the single-tenant setup, and an organisation that serves several runs several instances. Left to right is the order data moves. An arrowhead points at what is called or written to, and the FHIR side carries one at both ends because the bridge reads openEHR out to FHIR and writes FHIR back in. The other three servers call a FHIR terminology server, for three different reasons: FerroCHART to expand the value set behind a coded field so the form can offer the codes it admits, FerroEHR to validate a coded value at commit time, with $expand configured in its place against a server that does not offer $validate-code, and FerroBRIDGE to resolve a display, translate a code and validate one. That seam is the FHIR terminology API, so FerroTERM fills it and so does any other implementation. The facade speaks the FHIR release FHIRconnect's mappings name, and FerroBRIDGE's site says which. OMOP is a database schema, so its edge names no protocol: the OMOCL mappings compile to SQL that writes typed rows into the CDM tables.

The dashed boxes are the planned four. FerroEHR carries the SMART on openEHR layer today: the discovery document, the launch context, the scope grammar and the gate that enforces it. FerroSMART pulls that layer out into a server of its own. FerroCHART, as a SMART application, obtains its token and launch context there, and FerroEHR asks it whether each token it is handed may do what it asks; FerroTERM and FerroBRIDGE ask the same, and the picture leaves those two lines to this sentence. An application sends FerroFED an ordinary AQL query and never learns it was federated: the gateway asks FerroPIX where the record is (the index FerroEHR feeds each time it creates an EHR), then sends standard AQL to each node, the local FerroEHR or another organisation's CDR, and merges what comes back. An application that opens a record asks FerroPIX the same question; FerroCHART receives the EHR it is launched with and asks nobody. FerroSYS is drawn as a band under everything because every server reports to it and is configured from it, and a line from each would say nothing the band does not. Which release of each standard a product implements is on that product's site, rendered from its own pins.

What the family holds in common

The same four commitments in all four repositories

The four differ in what they do. They are built, licensed and evidenced the same way.

The standard is the interface

openEHR for the record, HL7 FHIR for exchange and terminology, OMOP for research. Where a specification publishes a machine-readable model, the code is generated from it, so a specification update is a regeneration.

One licence, no open-core tier

Every product is source-available under the Business Source License 1.1, with each capability in one repository and nothing held back for a paid edition. Free for non-commercial production; other production use needs a commercial licence, and each version becomes Apache 2.0 four years after it is published. What that means for you.

Measured, never typed

Conformance verdicts and performance figures are rendered into these sites from records committed to the repository, and a check fails the build when a page and its records disagree. Every number on these sites comes from a run.

One binary to operate

Each server is a single self-contained Rust binary in a minimal distroless image: no application server, no language runtime to patch, and no garbage-collection pause in the request path. What you deploy is what you read.

Quick start

The whole stack, from one file

Nothing to check out. Each command below names a product's latest release, so it runs the same after the next one is cut. Each product's site carries the full installation, the configuration, and the licensing each code system needs.

shell 
# FerroCHART's release compose file starts FerroCHART, FerroEHR with its
# PostgreSQL, and FerroTERM. Three products, three licences; the file's
# header says what the demo profile is for.
$ curl -LO https://github.com/rubentalstra/FerroCHART/releases/latest/download/compose.yaml
$ FERROCHART_CDR_URL=http://ferroehr:8080/ferroehr/rest/openehr \
  FERROCHART_TERM_URL=http://ferroterm:8080/r4 \
  docker compose --profile demo up
# then open http://localhost:8080

# FerroTERM alone. The image serves UCUM and the registries with no
# configuration, and its viewer is at /ui.
$ docker run --rm -p 8080:8080 ghcr.io/rubentalstra/ferroterm:0.1.3
# then open http://localhost:8080/ui
